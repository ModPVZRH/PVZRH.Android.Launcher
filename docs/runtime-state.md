# 整合包运行状态

`RuntimeCoordinator` 是界面、快捷方式和 Bootstrap 共用的运行状态入口。
它提供按游戏包名区分的 `StateFlow<RuntimeState>`，所有保存、切换及删除操作
在 IO 线程执行。任务不依赖 Compose 生命周期，提交过程不会因离开页面而取消。

`ModpackRuntimeStore` 负责文件布局和整合包归属，`DirectoryTransaction` 负责
暂存、提交、回滚及中断恢复。`ModpackManager` 保留整合包 CRUD、导入导出和元数据接口。

## 提交与恢复

- 同一进程用锁串行访问同一游戏目录，跨进程通过游戏目录中的 `.runtime.lock` 协调。
- 保存配置和日志也使用事务。配置按当前目录完整保存，已删除配置不会在下次恢复时重现。
- 切换先保存当前归属的状态，再准备目标插件、配置和附加文件。准备失败不修改运行目录。
- 提交前写入事务日志，随后将受影响的旧目录项重命名到备份区，再安装新目录项。
- 任一步骤失败会恢复旧目录项；进程中断后，下次访问先恢复未提交事务。
- `.launcher-runtime.properties` 与文件一起提交，记录实际整合包和附加文件清单。
  SharedPreferences 仅作为旧版本迁移来源和兼容镜像，不决定已有运行目录的归属。
- 已提交事务的备份清理失败时，下次访问继续清理。恢复失败时保留备份并报告错误。

事务暂存位于对应目录的 `.launcher-transaction/` 中。需要额外空间存放待部署的
插件、配置以及受影响的附加目录；框架核心、interop 缓存等不整目录复制。
这是带回滚的多目录项提交，并不保证未参与文件锁的游戏插件能观察到原子的目录切换。
游戏仍在运行时切换整合包的进程生命周期策略是独立问题。

## 附加文件归属

`plugins/`、`config/`、`logs/` 使用各自的状态规则。整合包额外提供的文件
（如 `patchers/` 中的 DLL）记录到部署清单，下次切换或进入原版时删除旧清单中的文件。
同目录中未记录的用户文件保留。框架核心、interop、Unity 库、桥接发现文件及诊断文件
不由附加文件部署覆盖；`core/` 依赖仍由 Bootstrap 的框架合并流程处理。

首次迁移从已知的旧整合包目录推导附加文件清单。无法确定来源的更早历史残留不会被
猜测删除。不要手工删除事务日志或备份目录；应让启动器执行恢复。

## 验证

```powershell
.\gradlew.bat :app:testDebugUnitTest
```

测试覆盖暂存失败、提交中途失败、进程中断恢复、附加文件隔离、框架及用户文件保留、
禁用 DLL、旧版本迁移、过期保存请求，以及多个存储实例的访问串行化。
Android 真机还需验证外部存储上的文件锁、目录重命名，以及带实际插件的启动流程。
